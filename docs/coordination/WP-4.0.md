## Why it is expand-only
- New columns are nullable, or NOT NULL with a constant default (`contact_visibility '{}'`, `created_by_member false`): old inserts and updates are unaffected and `ADD COLUMN` is metadata-only.
- New CHECKs constrain only the new columns, which 0003-era code never writes. CHECKs and the FK on the existing tables are added `NOT VALID` and then validated in the same transaction, like 0002/0003. New tables are empty, so their constraints are created valid.
- Nothing is dropped, renamed or narrowed. No data step. 0004 has not been deployed, so the PR #43 review changes were folded into it rather than added as 0005.

## Decisions
- **Date ↔ year rule: the year follows the date.** `birth_year`/`death_year` stay (ancestors often have only a year). A full date requires its year and must fall in it (DB CHECK, equality only). The **contract** fills a missing year from the date and rejects a mismatch; a death year/date without `deceased` sets `deceased: true` (or rejects an explicit `false`). The DB's existing year-range and death ⇒ deceased CHECKs therefore cover dates too. Dates are 1800–2200, like years.
- **`show_*` vs `contact_visibility`: keep the columns as the source of truth** for email, phone and city; `contact_visibility` stores only the seven new kinds (its CHECK rejects `email`/`phone` keys). The read model `ContactVisibility` has all nine keys (`toContactVisibility(showEmail, showPhone, stored)`); the write model `contactVisibilityInputSchema` accepts all nine (at least one when present) and the server maps `email`/`phone` to the columns. No backfill, no dual write, nothing to drop later.
- **Crop rect: optional, server-clamped.** `crop: { x, y, size }` in source pixels after EXIF rotation, integers ≥ 0, `size` ≥ 1, each ≤ 30 000, strict object. Only on `personPhotoConfirmInputSchema`; avatars can adopt `imageCropRectSchema` in WP-4.3. The web normally crops client-side (1024² JPEG) and omits it. When present, the server must use `clampCropRect(rect, width, height)`: `side = min(size, width, height)`, then the origin is **shifted** inside (`left ∈ [0, width − side]`, `top ∈ [0, height − side]`), not shrunk. It throws `RangeError` on non-integer image dimensions and non-finite rect values (direct callers).
- **Own-family circle = qualifying edges only (Security M1).** See ADR 0001 §6 for the precise rule. `person_relationships.created_by_member` records provenance at write time, so the circle does not depend on a creator's *current* role. Members cannot relate two existing people.
- **Handle rules in one constant.** `CONTACT_HANDLE_RULES` regex sources are anchored, ASCII, backslash-free (bracket classes, `(?:…)`), case-sensitive, and valid in both JS and Postgres ARE. The Drizzle schema builds the CHECKs from them; the migration test runs a corpus through both engines and asserts they agree. Inputs only strip whitespace and one leading `@`; a pasted URL is rejected, not parsed.
- **`buildContactCard` lives in `packages/types`** (pure). It re-validates every stored value and **drops** anything that fails, so a corrupt row never becomes a link; nothing is normalized at read time. `contactItemSchema.href` additionally only allows `https://…`, `mailto:` and `tel:+digits`. Website display uses `URL.host` (punycode for IDN lookalikes).
- **E.164.** `normalizePhoneE164` (input only): separators ignored; `+`/`00` = international; 10 digits = MX local (+52); `52`+10 digits; `521`+10 digits (old mobile prefix, the `1` dropped); anything else → `null`. At **read** time `buildContactCard` links only values already stored as E.164 (Security L1); a legacy free-form phone is dropped from the card until the backfill (backlog).
- **Contacts write path.** `PATCH /api/profile/me/contacts` (`updateContactsInputSchema`) is the only path the web uses for contacts, including `phone`. `PATCH /api/profile/me` keeps accepting `phone` for older clients (deprecated for phone) and validates it with the same `e164PhoneSchema`. WhatsApp is stored exactly as sent (`null` = none); the web pre-fills it from the phone, the server never infers it.
- **Person fields optional on the wire, required in `PersonDetails`.** Older PWA clients ignore unknown keys; newer clients parse older servers. `Person.avatarUrl` becomes the resolved photo in WP-4.3 (same field, so old clients show tree photos too). `GET /api/family/people/:id` returns `PersonDetails`.
- **New admin/member input schemas instead of extending the old ones.** The current admin routes pick fields explicitly, so extending `createPersonInputSchema` would silently drop dates. The new schemas are strict (unknown keys → 400).
- **Revision snapshots are typed** (`type: person | relationship | photo`), always carry `personId` (DB CHECK) and never contain object keys. Photo revisions are not revertible. Purge is by person (path `:id`) and also matches `fromPersonId`/`toPersonId`.
- **Admin routes keep the `/api/admin/people*` prefix** (no `/api/admin/family/*`).
- **Error detail codes**, not new `ErrorCode`s (closed enum; ADR 0001 §4).

## Security requirements (PR #43 review)
- **M1 (A01, circle escalation):** members create edges only together with a **new** person (`relateTo`), to someone already in their qualifying circle; no member relationship create/delete; the circle walks only qualifying edges (admin-created, or member-created where that member created an endpoint person); member deletes only of their own unlinked additions without other edges; living people's full dates and birthplace readable only within the same qualifying circle (plus self and admins). Tests in WP-4.1 must cover: a member cannot reach a non-relative through any sequence of member requests; a member-made edge whose creator did not create an endpoint (planted in the DB) does not extend the circle; deleting another member's addition → 403 `NOT_CREATOR`; deleting a person with other edges → 409 `PERSON_HAS_RELATIONSHIPS`.
- **L1:** `tel:` only for values already valid E.164; no +52 guess at read time; the +52 default is for input only. Covered by `contacts.test.ts` (incl. a US 10-digit legacy value).
- **L2:** admin-only purge of a person's revision history (`purgePersonRevisionsInputSchema`, `POST /api/admin/people/:id/revisions/purge`), working after the person is deleted; every snapshot carries `personId` (DB CHECK). The purge is audited with ids and the count only.
- **Info:** `clampCropRect` guards non-finite values for direct callers.

## Interfaces for 4.1–4.4

### WP-4.1 Family editing (BE + FE) — owns `PersonDetails`
- **Member routes (final list):** `POST /api/family/people` (`memberCreatePersonInputSchema`, create + `relateTo`), `PATCH /api/family/people/:id` (`memberUpdatePersonInputSchema`), `DELETE /api/family/people/:id`. **No member relationship routes.** `GET /api/family/people/:id` returns `PersonDetails`.
- **Admin routes:** `POST /api/admin/people` (`adminCreatePersonInputSchema`, `relateTo` nullable), `PATCH /api/admin/people/:id` (`adminUpdatePersonInputSchema`), `DELETE /api/admin/people/:id`, existing `/api/admin/relationships` (`createRelationshipInputSchema`), `GET /api/admin/people/:id/revisions` (`personRevisionsQuerySchema` → `Page<PersonRevision>`), `POST /api/admin/revisions/:revisionId/revert` (params `revertPersonRevisionInputSchema`, no body; 409 when already reverted or stale), `POST /api/admin/people/:id/revisions/purge` (body `purgePersonRevisionsInputSchema` → `PurgePersonRevisionsResponse`).
- **`RelateKind` → edge:** `parent_of`: new → anchor; `child_of`: anchor → new; `partner_of`: one `partner_of` edge. Same cycle and 2-parent checks under the advisory lock. Member edges set `created_by_member = true` and `created_by_user_id`.
- **Circle:** implement the ADR 0001 §6 rule server-side within `FAMILY_TREE_MAX_DEPTH`, over qualifying edges only.
- **Errors:** 403 `FAMILY_NOT_IN_CIRCLE`; 403 `PERSON_LINKED_TO_OTHER`; 409 `PERSON_HAS_RELATIONSHIPS` (member delete with other edges); 403 `NOT_CREATOR` (member delete of someone else's addition). Deleting a member-created person removes its edges in the same transaction.
- **`PersonDetails` builder:** permissions and privacy (`canEdit`, `canEditPhoto`, `isLinked` under the unlisted rule, living-people dates/birthplace by qualifying circle, bio for verified members); calls `resolvePersonPhoto(deps, { avatarKey, photoKey }, size)` (pass `avatarKey: null` when `canSeeAvatar` is false) and `personContactCard(row)` with `loadPersonContactRows(db, userIds)` only for verified viewers and linked, listed, active accounts. Also fill `Person.birthDate/deathDate/birthplace/bio` in `toPerson`.
- **Revisions:** write `person_revisions` in the same transaction as each change (`PersonRevisionSnapshot`, always with `personId`); for relationship actions set `relationship_id`, and `person_id`/`personId` = the new or edited person. Set `people.updated_by_user_id`. Retention job: delete rows older than one year.
- **Acceptance criteria:**
  - **Mandatory** server-side merged-row `personDatesIssue()` on **every** person write, including the deprecated admin routes and `PATCH /api/family/me`: no DB-constraint 500s.
  - The FE clears the date when its year is cleared.
  - Admin person delete also deletes the person's bucket photo objects (current derivatives and pending `person_photo_uploads` objects), and offers an optional "Borrar también el historial" checkbox that calls the purge.

### WP-4.2 Invites linked to people (BE + FE)
- Existing `adminInviteCreateInputSchema.personId` (nullable) is the field. Server checks → 400 `VALIDATION` with `details: [{ path: "personId", code }]`: `INVITE_PERSON_DECEASED`, `INVITE_PERSON_REQUIRES_BOUND` (open/multi-use invite with a person); already linked → 409 `CONFLICT` + `PERSON_LINKED_TO_OTHER`.
- Picker data: `PersonDetails.isLinked`, `deceased`, years (admins see all), or a dedicated admin search; WP-4.2 owns any `AdminInvite` read-model extension ("who it's for").

### WP-4.3 Photos with crop — implements `resolvePersonPhoto`
- Table `person_photo_uploads` (`personPhotoUploads`); columns `people.photo_key`, `photo_updated_at` (`people_photo_check` requires both).
- `POST /api/family/people/:id/photo/uploads` (`personPhotoUploadInputSchema` → `PersonPhotoUploadResponse`), `POST /api/family/people/:id/photo/confirm` (`personPhotoConfirmInputSchema`, optional `crop` → `clampCropRect` before `extract()`) → `PersonDetails`, `DELETE /api/family/people/:id/photo` → `PersonDetails`. Admins use the same routes with full scope. Optionally add `crop: imageCropRectSchema.exactOptional()` to `avatarConfirmInputSchema`.
- Replace the `TODO(WP-4.3)` in `modules/family/personPhoto.ts` (signature fixed). `canEditPhoto`: admin, close relative over qualifying edges (parent/child/partner), or the linked person.
- Write a `person.photo` revision (`PersonRevisionPhotoSnapshot`, no keys; not revertible). Reuse the avatar cleanup job for expired pending rows.
- **Acceptance criteria:** the admin person delete (WP-4.1) deletes photo objects through a helper this WP exposes; non-finite or oversized crops never reach sharp.

### WP-4.4 Directory contacts — implements `loadPersonContactRows`
- Columns `profiles.whatsapp…website`, `contact_visibility`. `PATCH /api/profile/me/contacts` (`updateContactsInputSchema`): `visibility.email/phone` → `show_email/show_phone`, the rest merged into the jsonb; WhatsApp stored as sent. Own read: `OwnProfile.contacts` (`OwnContacts`, `toContactVisibility`). `PATCH /api/profile/me` keeps `phone` for old clients (now E.164-normalized).
- Directory/tree read: `DirectoryEntry.contacts` and `PersonDetails.contacts` via `personContactCard(row)` / `buildContactCard`, only for verified viewers and listed, active accounts. Directory search keeps ignoring contacts. Replace the `TODO(WP-4.4)` in `modules/family/personContacts.ts`.
- `ContactList` renders `href` as-is with `rel="noopener noreferrer nofollow"`; labels from `item.label`. The FE pre-fills WhatsApp from the phone.

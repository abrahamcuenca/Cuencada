# WP-5.3 Events server + chat/media scoping [SEC]
Owner: Senior JS backend (security) · Reviewers: TL, Security · Branch: `wp/5.3-events-server` · PR: (not opened)

Based on `origin/main` @ 484405d (WP-5.1 + WP-5.2). Implements every route of `docs/coordination/WP-5.2.md` under ADR 0001 §7 and the WP-5.3 security requirements 1–12. Migration **`0009`** (expand-only). WP-5.4 (web) runs in parallel against the same contracts; this WP adds one contract (the consent notice, below) and touches no web code.

## Routes
All member routes are `auth: "user"` + `requireVerifiedEmail`; admin routes `auth: "admin"`. Exactly the WP-5.2 table, plus the two notice routes:

| Route | Notes |
|---|---|
| `GET /api/events/notices` | **new** (consent notice, requirement 3) → `eventNoticeListSchema` |
| `DELETE /api/events/:id/notice` | **new**: dismiss the caller's notice, 204, idempotent; 404 when invisible |
| everything in WP-5.2's table | as specified; `POST /api/events/:id/albums/:albumId/uploads` answers **201** like the edition intent |

## Decisions
1. **One visibility predicate.** `eventVisibleSql(viewer, table)` (published+members → everyone; published+participants → participants; draft → organizers; hidden → nobody; admins → all) and `eventMemberAccessSql` (visible and participant, or admin) are the only rules; chat rooms and the media scope reuse them through table aliases. Reads load the event through the predicate in one statement; writes `select … for update` the row and then **always** run the same visibility query, so unknown and invisible ids take the same path to 404 `EVENT_NOT_FOUND`. Fastify's body schema runs before the handler but never depends on the event.
2. **Consent notice (requirement 3): no notifications table yet.** No notification mechanism existed. The notice is derived from the caller's own `event_participants` row: `added_by_user_id` is someone else, `notice_seen_at` (new nullable column, 0009) is null, and the event is visible to the caller (so a notice never names an event they cannot open). Members added to `members` events get one too (wider than requirement 3). "Salir" is the existing `DELETE …/participants/me`; leaving deletes the row and the notice; a re-add creates a fresh one. A notice disappears if the adder's account is removed (`added_by_user_id` is set null). Everything lives in `events/notices.ts` + two routes + the column, so **WP-6's general `notifications` table** can replace it (backlog item).
3. **Fan-out (requirement 6).** `ChatHub.fanOutRoom(roomId, frameFor)` is the only path for room frames; the old global `fanOut` is now private and used for presence only. Audiences: global and edition rooms → every connected member (each inbound frame re-checks visibility; kind never changes, cached forever); event rooms → `loadRoomAudience` (participants with access: published → all, draft → organizers, hidden → none; plus active admins), cached 60 s. Every participant/role/status/visibility write snapshots the readers **before** its transaction and awaits `syncEventRoom` **after** the commit and **before** answering: the hub reloads the set, bumps the room's generation and sends `room_removed` (and forgets typing state) to every connected user who lost access. Refreshes of a room are serialized; a fan-out whose load raced a refresh sees the generation move and reloads, so it never sends with a stale set (unit test `chat/audience.test.ts`). Delete uses `removeRoom` (everyone who could read it). A refresh failure after commit drops all cached event audiences (fail safe: next fan-out reloads). An admin role change updates the live principals and drops the cached audiences. Single process, like the rest of the hub (backlog).
4. **Admin-view audit (requirement 5).** New table `event_admin_views (admin_user_id, event_id, hour_bucket)` (PK, cascades). `auditAdminEventView` runs one transaction: check the event is `participants` and the admin not a participant → insert-on-conflict-do-nothing → only if inserted, `recordAudit(event.admin_viewed, { surface })` → prune that admin's older buckets. Called **before** building the response on the detail, chat history, album media list and album media by id; any error fails the read (500) and rolls the dedupe key back.
5. **Media scope (requirements 1, 7, 10, 12).** `mediaScopeSql(viewer)`: edition rows unchanged, album rows only with event access; applied to GET/PATCH/DELETE by id, confirm, report and the admin list. The DELETE route now loads through the scope too (it used an unscoped query). New edition rows also store `storage_prefix = cuencadas/{year}`. Confirm rejects (`prefix_mismatch`, audited `media.upload_rejected`) a row whose original key is not `mediaKeys(row prefix, id)`. Album intents go through `createPendingUpload`, the same advisory-locked budget step as edition uploads (one budget), and re-check participation inside that lock.
6. **Deletes.** Album delete: 409 `EVENT_ALBUM_NOT_EMPTY` with live media, else hard-deletes soft-deleted rows (locked) and deletes their objects after the commit. Event delete: hard-deletes the album media rows (RESTRICT FK) in the transaction, then deletes the event (cascade), then the media objects, cover derivatives and every cover upload's original/derivatives after the commit (best effort; the media sweep retries album keys).
7. **Cover (requirement 8).** `processImage` mirrors `processSquareImage` (format and 24 MP cap from the header, `.rotate()` → `clampAspectCropRect` → resize → WebP without metadata, shared semaphore). Intent/confirm/delete copy the person-photo routes; confirm is uploader-only (404) and re-checks organizer/admin before decoding and under the event lock; replaced/removed derivatives and the original are deleted. `coverKeyForWidth` presigns only keys this module wrote and only inside visible responses.
8. **Slugs (requirement 11).** `insertEventWithSlug` tries each `memberEventSlug` in a savepoint; a `(year, slug)` collision retries with a fresh suffix up to `EVENT_SLUG_MAX_ATTEMPTS`, then a plain `Error` → generic 500 `INTERNAL`. Admin typed slugs → 409 `EVENT_SLUG_TAKEN`. A year change that collides keeps a typed slug (409) or regenerates a member slug. `slugSuffixSource` is a test seam.
9. **Participants (requirements 2, 4).** Non-admin organizers add only listed, active, verified members; admins active, verified members (stricter than "any active": unverified accounts could not open the event anyway). Any ineligible id → one generic 400 (no oracle on hidden accounts). Existing participants are skipped. Cap 200 (409). Last organizer: 409 `EVENT_LAST_ORGANIZER` on leave, demote and remove (under the row lock). `EventParticipant.userId` for self, managers and listed active members; `avatarUrl` for self and listed active members; never email or contacts.
10. **Rate limits.** Creation: database counts under a per-user advisory lock, 10 per rolling day and 20 open drafts (admins exempt), plus 20/h per route. Participant writes (join, leave, add, role, remove): one shared per-user counter, 100/h. Event/album writes 120/h, album intents 60/h (plus the gallery caps), cover routes reuse the avatar limits.
11. **Audit.** One `event` entity type; metadata only ids, enums, field names, counts (`event.created` `{status, visibility, participantCount, typedSlug}`, `event.updated` `{fields, status, byAdmin}`, `event.published`, `event.hidden {hidden}`, `event.deleted {participantCount, mediaDeleted, byAdmin}`, participant actions with user ids and roles, album ids, cover upload ids). Tested not to contain titles or names.

## Rollout
Migration 0009 is expand-only (a nullable column and a new table; 0008-era code never touches them) and ships with this code. Media by-id scoping lands together with the album upload route, so album rows never exist without the scope check.

## Coordination with WP-5.4
- New contract (`packages/types/src/events.ts`): `EventNotice`, `eventNoticeSchema`, `eventNoticeListSchema`, `EVENT_NOTICES_MAX`; routes in the table above.
- `POST …/albums/:albumId/uploads` is 201; `DELETE /api/events/:id` and `DELETE …/participants/me` are 204; the other writes return `EventDetail`.
- Removing or demoting yourself so that you lose access answers 404 on the follow-up detail (backlog note); treat as "left".

## How Acleron deploys this project (read-only findings)

The platform is the sibling checkout `../acleron-platform/acleron-platform`,
reached through `mise.toml`. In bundle mode:

1. `build-bundle.sh` runs on the **operator's machine**: `mise run verify`,
   then `build_command` with `build_env`, then **`server.migrate_command`
   against production through the SSH tunnel**, then it packs the bundle.
   - It refuses a `MIGRATE_DATABASE_URL` that isn't
     `deploy.migrate_tunnel`, and it refuses a migration hidden in
     `build_command`. It never reads the vault.
   - A failed migration ships nothing.
2. `deploy.yml` (Ansible) then:
   - checks that the manifest says the migrations were applied;
   - uploads the bundle and runs `pnpm install --prod --frozen-lockfile --filter <runtime pkg>...`
     **on the VPS**, so native modules are installed there;
   - swaps the `current` symlink and rsyncs the SPA to `frontend.public_root`;
   - renders the systemd unit (mode 0600, one `Environment=` line per
     `server.env` key, with vault values substituted), restarts it and waits
     for `is-active`;
   - runs certbot `--webroot` (first run only);
   - renders the nginx site from **its own template**, then `nginx -t` and a
     reload.
3. nginx and systemd are generated by Acleron, not hand-managed. The stock
   nginx template has no hook for project directives. The systemd unit has
   none either, but systemd drop-ins are never touched by it.

What this means here:

- The stock nginx template **breaks chat**: it upgrades only `/ws`, and the
  socket is `/api/chat/ws`. It also has no CSP, appends XFF and logs query
  strings.
- So the project ships its own site and needs a small platform change
  (`nginx.site_template`, [nginx.md](../deploy/nginx.md)). Until it lands,
  `deploy-preflight` blocks the deploy.
- `mise run deploy-check` used to be `ansible-playbook --check --diff`. The
  diff of the rendered systemd unit prints every vault secret, so that task is
  now `deploy-dryrun`, without `--diff`, and `deploy-check` is a local,
  secret-free gate.

## Decisions

- **D1. Bucket name, endpoint and region are literals in `project.yml`, not
  vault values.**
  - They aren't secrets: the bucket host is in the CSP header and in every
    presigned URL.
  - `build_env` can't read the vault anyway.
  - Keeping them literal lets the preflight prove that
    `VITE_MEDIA_UPLOAD_ORIGIN`, `S3_BUCKET`, `S3_ENDPOINT` and the nginx CSP
    all agree.
  - The access keys stay in the vault. The placeholder is `<bucket>`, and the
    preflight fails until it's replaced.
- **D2. The project owns its nginx site** (`infra/nginx/cuencada.conf`), with
  no template markers so it is valid with or without Jinja.
  - The CSP is copied byte-for-byte from `csp.md` into the three static
    locations, and the preflight test catches drift.
  - Cache-Control comes from a `map`, so no fourth copy of the headers is
    needed.
  - `/api/` gets no nginx headers. Helmet's API set is stricter, and adding
    nginx's would duplicate them.
- **D3. `/index.html` is not redirected.** It is the SPA shell, and Workbox
  precaches it as `/index.html?__WB_REVISION__=…`, so it must answer 200.
  `/cuencada2026.html`, `/mensajes.*` and `/images/fotos/*` are redirected.
- **D4. Only the shallow `/healthz` is public** (it proxies `/health`, with no
  DB call). `/health/ready` is loopback-only and checked over SSH. This
  follows the threat model's "restrict `/health*`" and Acleron's
  `health_path` convention.
- **D5. The seed runs as the owner role, over the tunnel, after the first
  migration.**
  - It only inserts rows. The runtime role's grants were proven separately.
  - In production, all four `SEED_*_URL` are now **required**, and the error
    names only the missing variables.
  - `SEED_ALLOW_MISSING_LINKS=true` is the explicit opt-out for a re-run.
  - The legacy links were removed from source. Dev and test use
    `https://example.com/cuencada-dev/*`.
- **D6. Video cap 150 MB, decided on facts rather than a guess.**
  - The read-only facts scan of `server_1` on 2026-10-06 showed **961 MB of
    RAM in total** and 76 MB `MemFree`, with nine other Node services running.
  - The planned rule was "if under 700 MB free, lower the cap". Free memory
    cannot reach 700 MB on that host, so the cap is now 150 MB.
  - The DB CHECK keeps 300 MB (a literal in the schema), so raising the cap
    back after storage streaming lands needs no migration.
  - systemd sets `MemoryHigh=400M` and `MemoryMax=550M`. **Recommendation:**
    add 1 GB of swap or move to a 2 GB plan before launch.
- **D7. Native modules (argon2, sharp) match the VPS.**
  - The VPS installs them itself from the lockfile:
    - argon2 0.44 ships `linux-x64` glibc and musl prebuilds, and its build
      script is allowed;
    - sharp 0.35 installs `@img/sharp-linux-x64` and `@img/sharp-libvips-linux-x64`,
      which need glibc ≥ 2.26.
  - The VPS runs Ubuntu 24.04 (nginx/1.24.0 (Ubuntu) banner) on x86_64. The
    build machine runs glibc 2.39 on x86_64, and `build-bundle.sh` refuses any
    other platform.
  - Both modules loaded and ran under the hardening flags with
    `UV_THREADPOOL_SIZE=6` (`systemd-run --user`).
- **D8. `UV_THREADPOOL_SIZE=6`.**
  - argon2, sharp's async work and DNS/fs share libuv's pool of 4. That
    sharing caused the WP-2.2 contention (a caption save took about 13 s
    while images processed).
  - sharp is already `concurrency(1)` with no cache. Avatars process at most
    2 at a time.
  - 6 lets logins and DNS through while an image job runs. More threads would
    add memory, not throughput, on this host.
- **D9. DB roles.**
  - `cuencada_owner` owns everything. It is used only as
    `MIGRATE_DATABASE_URL` (the operator, through the tunnel).
  - `cuencada_app` is the runtime role:
    - DML only, plus sequence usage and default privileges for future tables;
    - no DDL, `TRUNCATE`, temp tables or `drizzle` schema;
    - `statement_timeout` 30 s, `idle_in_transaction_session_timeout` 60 s,
      a connection limit of 30;
    - it is `NOINHERIT`.
  - The passwords are hex: no URL-escaping, and no `%`, which systemd would
    treat as a specifier.
- **D10. Lifecycle without a prefix expiry.** The media code writes originals
  straight to `cuencadas/<year>/originals/` (there is no `incoming/` prefix;
  checked in `files.ts`). Only `AbortIncompleteMultipartUpload` after 1 day is
  safe. The cleanup job handles orphans.
- **D11. Legacy site.** It isn't served anywhere today:
  - `cuencada.com` resolves to `server_1`, which has no cuencada vhost and
    answers with `acleron.com`'s default site and certificate;
  - `/cuencada2026.html` and `/mensajes.txt` return 404;
  - there is no GitHub Pages site.

  Retiring it means a `git rm` PR after the cutover, plus the nginx
  redirects. History stays.

## Open questions (→ owner)

1. **Bucket name.** It goes in `project.yml` (2 lines) and
   `cuencada.conf` (3 lines). The preflight blocks until it is set. Is the
   bucket created yet, and is the access key limited to that bucket?
2. **Server memory.**
   - `server_1` has 961 MB in total for ten Node services. Please run
     `free -m` (the `available` column).
   - Add 1 GB of swap, or move to a 2 GB plan before launch?
   - The 150 MB video cap is already in this branch. Say so if you want 300 MB
     back and accept the risk.
3. **Where Postgres 18 runs.** The read-only facts scan shows **no
   `postgresql.service` and no listener on :5432 on `server_1`**. Is the DB on
   another host, a container, or a non-default port?
   - The runtime `DATABASE_URL` host and the `pg_hba` rules depend on it.
   - **Tunnel port:** `deploy.migrate_tunnel` is set to Acleron's default
     `127.0.0.1:15432`. Confirm it, or give the port your `db` alias uses.
4. **Resend.**
   - Is the account created and `cuencada.com` added?
   - Who manages DNS for `cuencada.com`?
   - Is there a mailbox for `admin@cuencada.com`? The seeded admin starts
     unverified and must click a verification email before chat and the
     gallery work.
   - Which address should receive DMARC `rua` reports (proposed:
     `admin@cuencada.com`)?
5. **Platform change.** OK to add `nginx.site_template` to `acleron-platform`
   (about 6 lines, opt-in, see nginx.md)? Or use the interim manual install
   after each deploy?
6. **Breached-password check (L5).** Build it before launch (offline top-100k
   list, or HIBP k-anonymity), or waive it in writing for the first launch?
7. **Observability.** Does `server_1` already ship journald to Loki (Alloy or
   promtail)? The LogQL alert rules are ready in runbook § 10.

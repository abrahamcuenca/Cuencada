# ADR 0001: Shared zod contracts, response schemas as PII guard, token transport, error envelope

- Status: accepted (WP-0.2)
- Date: 2026-10-06
- Deciders: Software Architect, reviewed by Tech Lead and Security

## Context

Phase 1 builds frontend and backend tracks in parallel. They need one contract they cannot drift from. The server also handles PII (directory contacts, family tree, RSVPs) and single-use tokens (invites, magic links, password reset, email verification). In the scaffold these were handled ad hoc: inline zod in routes, `{ error: "string" }` bodies, and a stub that leaked a token-hash prefix.

## Decisions

### 1. zod 4 schemas live in `packages/types`

- `packages/types/src/<module>.ts` holds, for each module:
  - zod **input** schemas (`xxxSchema`, with input types `z.infer<typeof xxxSchema>`)
  - JSDoc'd **response interfaces** with a matching zod schema checked by `satisfies z.ZodType<Interface>`
  - unions as an `as const` object plus `z.enum(obj)`, never a TS `enum`
- The package is ESM. Source imports use `.js` suffixes and the package compiles with `NodeNext`, so the server (NodeNext) and Vite (bundler) both consume `dist/`. zod is a runtime dependency (`^4`, same major as the server).
- The web uses the same input schemas for forms, so client and server validation cannot drift.
- Defensive limits are mandatory:
  - Every string has a `max`. Text is trimmed, and emails are trimmed and lowercased *before* validation (`emailSchema`).
  - Admin-entered links must literally start with `https://`, have no userinfo and a dotted host. They are stored as the canonical `URL.href`. This blocks `javascript:`/`data:` and `https://cuencada.com@evil.com` lookalikes.
  - Names and file names are NFC-normalized and reject bidi controls and invisible characters (`displayTextSchema`). Chat bodies strip them instead, keeping ZWJ for emoji.
  - Uploads use an allowlist of MIME types (JPEG, PNG, WebP, MP4, QuickTime; no HEIC) and per-kind size limits (image 25 MB, video 300 MB).
  - Lists returned in `details` are capped at `API_ERROR_DETAILS_MAX` (100).
- Every input schema exports two types: `XxxInput = z.infer` (parsed output, for the server) and `XxxRequest = z.input` (pre-defaults and pre-coercion, for RTK Query args and forms).
- PATCH inputs are built from field maps **without defaults** and then `.partial()`, so a partial update never resets omitted fields to their defaults.
- `src/index.ts` re-exports every module and is **frozen** after this WP. Phase-1 tracks edit only their own module file.

### 2. Response schemas are the PII guard

- Every route declares a response schema through `fastify-type-provider-zod`. zod objects strip unknown keys, so a column that is accidentally selected (for example `passwordHash`, `showPhone`, or a hidden phone) is never serialized.
- `DirectoryEntry` contact fields (`email`, `phone`, `city`) use `exactOptional()`. They are **absent** when hidden, not `null`, so a member can't learn that a field exists but is hidden.
  - The service must build entries with `toDirectoryEntry()`, which omits each field unless its `show*` flag is on.
  - The schema rejects `undefined`/`null` contact values, so a hand-rolled mapper fails closed with a 500 instead of leaking. The schema is defense in depth, not the only check.
  - Directory search must match only fields the target has made visible.
- Response datetimes are ISO strings with an offset. The server converts `Date` values before replying, and serialization fails closed (500) on a mismatch.

### 3. Tokens travel in the body (and the URL fragment), never in the path or query

- Emails link to `https://cuencada.com/<page>#t=<opaque>`. The SPA reads the fragment and POSTs `{ token }` to `/api/invites/inspect`, `/api/invites/accept`, `/api/auth/magic-link/consume`, `/api/auth/password-reset/confirm`, or `/api/auth/email/verify`.
  - *Note (WP-0.5.1, orchestrator decision):* `#t=` is the canonical fragment name, and it is what `@cuencada/emails` generates. Earlier drafts said `#token=`.
- Fragments are never sent to the server or in `Referer`, so tokens stay out of access logs and proxies. Email link scanners don't consume them, because a GET does nothing.
- The refresh token exists only in the `__Secure-cuencada_rt` cookie (HttpOnly, Secure, SameSite=Strict, Path=/api/auth). It is never in a JSON body. Refresh and logout also require the `X-Cuencada-CSRF` header and an exact `Origin` match. The access token is returned in the body and kept only in memory.
- **Refresh rotation threat note (T1, PR #14; grace re-issue since WP-4.6):**
  - Refresh tokens are single-use. Rotation marks the presented token `used_at` and links `replaced_by_token_id` to its successor.
  - **Grace re-issue (WP-4.6).** A used token presented again **within 10 s** (`REFRESH_REUSE_GRACE_MS`) is a client that lost the rotation response: a page reload aborted the refresh after the server committed, or a second tab refreshed at the same moment. If its **immediate** successor (same session) is still unused and unexpired, the server rotates that successor too (marks it used, links a new token) and answers 200 with a fresh cookie and access token for the **same** session. Audited as `auth.refresh_grace_reissued` (session id; `presentedId`/`successorId` are `refresh_tokens` row ids, never token material).
    - *Before WP-4.6* this answered 409 `REFRESH_RACE`; the client waited 11 s and retried, which by then was reuse, so a member who reloaded right after a refresh (a slow phone) was logged out and the session revoked. That was the intermittent e2e journey 11b.
  - **Grace is spent once.** The same token presented again finds its successor used: reuse. So does an older token whose successor was rotated normally (only the immediate predecessor of the live token qualifies), and a used token whose successor is missing from its session (fail closed). Reuse after the window is unchanged. Reuse revokes the whole session (`refresh_reuse`), is audited as `auth.refresh_reuse_detected` with `metadata.reason` = `after_grace` | `successor_used` | `successor_missing`, and answers 401.
  - **Locking:** the refresh locks the token's **session** row first (`FOR UPDATE`), then its token rows. Every token write of a session happens under that lock, so concurrent refreshes (two tabs) serialize: one rotates, the other gets the grace re-issue. A third concurrent use of the same token is reuse. Browsers with Web Locks never send concurrent refreshes (`cuencada-refresh` lock).
  - The CSRF header and exact `Origin` check run before any of this (`auth: "cookie"`), so the grace path is not reachable cross-site. The route config is unchanged.
  - **Accepted risk (revised):** a thief holding a stolen token can, within 10 s of the victim's rotation, get one grace re-issue, i.e. a working chain until the victim's next refresh (at most the 15 min access-token lifetime later, or never if the victim does not return). Then one side presents a used token, reuse is detected, and the whole session, including the thief's chain, is revoked. Before WP-4.6 the thief got a 409 instead, but a thief who replays the token *before* the victim already got a working chain under both designs; the cookie is HttpOnly, Secure, SameSite=Strict with `Path=/api/auth`, so stealing it at all needs a compromised device or browser. Binding the grace to the session's User-Agent was considered and left out (a browser update would turn a reload into a logout; it adds little against a thief who has the cookie jar).
  - Used tokens of live sessions are never purged, so reuse detection works however old the replayed token is.
- **The one exception** is the WebSocket ticket. Browsers cannot set headers on a WS upgrade, so the 30-second, single-use ticket from `POST /api/chat/ticket` goes in `?ticket=`. The ticket is bound to the issuing session, so revoking the session invalidates unused tickets. The server must redact `ticket` from request logs, burn the ticket on first use, and check `Origin` on upgrade. App-level redaction doesn't cover the VPS reverse proxy, so WP-2.4 must also strip the query string from proxy access logs for `/api/chat/ws`.
- **Invites.** Holding an invite token must not be enough to claim someone else's identity:
  - `POST /api/invites/inspect` returns only `emailMasked` (`maskEmail`: `t***@e***.com`), never the full bound address. The invitee has to type it, and `accept` compares it after `emailSchema` normalization.
  - Admin invites must be email-bound, single-use and sent by email (`sendEmail: true`, no copy-link). Holding an admin token therefore implies controlling that mailbox.
  - `emailVerified` is set on accept **only** when the invite was bound to that email **and** delivered by email. Copy-link and open invites leave it `false` until the user verifies.
  - Open member invites are limited to 10 uses and 72 hours (defaults: 5 uses, 72 h), and every acceptance alerts all active admins (WP-2.3b owner decision; originally 20 uses and 14 days, see below).
- Request-for-token endpoints (magic link, password reset) always answer 202 `{ ok: true }`, so they reveal nothing about which accounts exist.

### 4. Error envelope and codes

- Every non-2xx response is `ApiError`: `{ error: { code, message, details? } }`.
  - `code` comes from the `ErrorCode` as-const object, with its HTTP status fixed in `errorHttpStatus`.
  - `message` is Spanish, produced server-side, and safe to show to the user.
  - `details` lists `{ path, message, code? }` for validation failures. `code` is an optional
    reason for the few cases the web branches on. The schema accepts any string (≤ 64 chars) so older
    clients still parse new codes; the known values are `ValidationIssueCode`, today only `PASSWORD_BREACHED`
    (WP-2.3c: the new password is in known breaches; the web shows the Spanish message on that field).
    The check is server-side and deliberately uncached, so its response time reveals nothing about
    earlier attempts with the same password.
- The web branches on `code` only. Notable codes:
  - `TOKEN_EXPIRED` (401): the client refreshes and retries.
  - `UNAUTHENTICATED` (401): the client logs out.
  - `PASSWORD_CHANGE_REQUIRED` (403): the client routes to `/cambiar-contrasena`.
  - `REFRESH_RACE` (409): no longer sent by the server since WP-4.6 (grace re-issue, §3); kept in the contract for older builds. The client retries after about 1 s, at most twice, then logs out locally.
  - `INVALID_CREDENTIALS`, `INVITE_INVALID` and `TOKEN_INVALID` are deliberately generic.
- Messages never contain stack traces, SQL, token material or other users' data. The server should call `z.config(z.locales.es())` for default messages. The contracts set explicit Spanish messages where the wording matters.

### 5. Undated editions: status `announced` (WP-3.1a note)

- An edition can be published before its date and place are decided (migration 0003). `startsAt`/`endsAt` are **both set or both `null`** (DB CHECK `cuencadas_dates_check`, the contract's both-or-neither refine, and a merged-row check on PATCH). `city`/`state` may be `null` independently.
- `CuencadaStatus` gains **`announced`**: published with no dates. It is computed like the others, never stored: `draft` (unpublished) → `announced` (no dates) → `upcoming` / `active` / `past` (calendar days in the edition's timezone).
- `HomeMode` gains `announced`. Home features, in order: an active edition, the soonest dated upcoming one, then the announced edition with the lowest year ≥ the current year **in that edition's timezone** (an announcement for a year already over is stale and ignored), else memories. `latestPast` is still returned so Home can link to the last edition's memories.
- Read models (`CuencadaSummary`, `PublicCuencada`, `AdminCuencada`) type the four fields as nullable. `DatedCuencada<T>` and the `hasDates()` guard (exported from `cuencadas.ts`) narrow an edition before anything date-dependent; the web's countdown, `countdownInstants` and the RSVP form accept only the narrowed type, so a `null` date cannot reach them at compile time.
- **RSVP:** writes for an announced edition answer 409 `CONFLICT` with the Spanish message "Las confirmaciones abren cuando se anuncie la fecha." and a stable reason in the open detail-code channel of §4: `details: [{ path: "cuencada", message, code: "RSVP_DATES_PENDING" }]` (`RsvpIssueCode.DatesPending` in `rsvp.ts`). `ErrorCode` itself is a closed enum that older clients validate, so no new top-level code was added. A future deadline does not open RSVPs without dates (there is no stay window to check against). `GET …/rsvp/me` answers `editable: false`; attendees and the RSVP summary keep working.
- The admin dashboard's "next edition" (`AdminSummaryEdition.startsAt: string`) still lists only dated editions: an announced one has no RSVPs to count.

### 6. Family people, own-family circle, photos, contacts and revisions (WP-4)

Contracts and migration 0004 come from WP-4.0 (details in `docs/coordination/WP-4.0.md`); WP-4.1–4.4 implement them.

- **People model.** A `people` row is a tree node with or without an account (`user_id` nullable, unique). WP-4 adds `birth_date`/`death_date` (`date`), `birthplace` (≤ 120), `bio` (≤ 1000), `photo_key`/`photo_updated_at` and `updated_by_user_id`.
  - **Year follows date.** The year columns stay (many ancestors only have a year). When a full date is set, its year must equal `birth_year`/`death_year` (DB CHECK). The contract fills a missing year from the date and rejects a mismatch. A death year or date implies `deceased` (the contract sets it when omitted). **Every** person write, including the deprecated admin routes, re-checks the merged row with `personDatesIssue()` on the server, so a CHECK never surfaces as a 500. The web clears a date when its year is cleared.
  - New `Person` fields are optional on the wire (older clients and servers interoperate); `PersonDetails` carries all of them plus `photoUrl`, `photoSource`, `isLinked`, `canEdit`, `canEditPhoto` and `contacts`. `GET /api/family/people/:id` returns `PersonDetails` (a superset of `Person`).
- **Own-family circle** (Security M1, PR #43). Computed on the server (WP-4.1) for the member's **self** = the person linked to their account. The circle is self, self's partners, children and parents, and the ancestors of self and of self's partners, recursively up, within the tree depth bound (`FAMILY_TREE_MAX_DEPTH = 4` generations). It is walked **only over qualifying edges**:
  - an edge with `person_relationships.created_by_member = false` (admin-created; every pre-0004 edge) always qualifies;
  - an edge with `created_by_member = true` qualifies only while `created_by_user_id` is not null **and** equals `people.created_by_user_id` of one of its endpoints (the member created the new person the edge was made for). Anything else (including after the creating account is deleted) does not qualify: fail closed, an admin can re-create the edge.
  - **Members never create or delete an edge between two existing people.** Their only edge-making path is `POST /api/family/people` with `relateTo`, which creates a **new** person and the edge in one transaction (`created_by_member = true`); `relateTo.personId` must already be in the qualifying circle. Relating existing people is admin-only (`createRelationshipInputSchema`, `/api/admin/relationships`). A "member proposes a link, admin approves" flow is in the backlog.
  - A member may **edit** anyone in the qualifying circle except people linked to **another** account (only that member or an admin: 403 `PERSON_LINKED_TO_OTHER`). Outside it: 403 `FAMILY_NOT_IN_CIRCLE`.
  - A member may **delete** a person only if they created it (`people.created_by_user_id`, else 403 `NOT_CREATOR`), it is unlinked, and its only edges are member-created ones made with it by that member (else 409 `PERSON_HAS_RELATIONSHIPS`); its edges are removed in the same transaction. Everything else is admin-only. Members cannot delete edges on their own.
  - **Read access** to living people's full dates and birthplace follows the same qualifying circle (plus self and admins); deceased people's are shown to verified members.
  - Members never set `userId`. Admins have full scope.
- **Photo precedence.** The linked account's own avatar wins; else the person's tree photo; else none. `Person.avatarUrl` and `PersonDetails.photoUrl` are that resolved photo (`resolvePersonPhoto`, `modules/family/personPhoto.ts`), under the existing unlisted/disabled rules for linked accounts. A tree photo is kept when the member removes their avatar, so it shows again. Tree photos are uploaded by admins, close relatives (parent, child, partner, over qualifying edges) or the person once linked, through the avatar pipeline. An optional crop rect (integers, source pixels) is clamped server-side with `clampCropRect` (side capped to the shorter image side, origin shifted inside); the web normally crops client-side and omits it.
  - **WP-4.3 (implemented):** routes `POST /api/family/people/:id/photo/uploads`, `POST /api/family/people/:id/photo/uploads/:uploadId/confirm` (the upload id in the path; body `personPhotoConfirmBodySchema` = optional `crop`) and `DELETE /api/family/people/:id/photo`, all returning `PersonDetails`. Close relatives may set the photo of people **without an account** only; a linked person's photo is theirs (or an admin's) to change. Tree photos are 512/256/64 px WebP; `resolvePersonPhoto` accepts 512 (an avatar asked at 512 is served at 256). A linked person's tree photo follows the avatar's unlisted/disabled rules. Avatars accept the same optional `crop` (`avatarConfirmInputSchema.crop`).
- **Contact visibility.** Contacts are stored as handles (social networks), E.164 (phone, WhatsApp) and canonical `https://` (website). The handle regexes are one exported constant (`CONTACT_HANDLE_RULES`) used by zod **and** the DB CHECKs. Each contact has its own switch, default hidden. `show_email`/`show_phone`/`show_city` stay the source of truth for those three; `contact_visibility` jsonb holds only the seven new kinds (its CHECK rejects other keys and non-boolean values), so nothing is stored twice. Members see a `ContactCard` (`{ kind, label, href, display }[]`) built only by `buildContactCard()` from fixed per-kind templates; clients never build links from raw values. `buildContactCard` links only values that already satisfy their rule: a legacy phone that is not stored as E.164 is **dropped** (never re-guessed as +52 at read time; Security L1). Verified members only, and never for unlisted or disabled accounts.
  - Writes: `PATCH /api/profile/me/contacts` is the only path the web uses for contacts, including `phone`. `PATCH /api/profile/me` still accepts `phone` for older clients (deprecated for phone) and normalizes it with the same `e164PhoneSchema`. WhatsApp is stored exactly as sent (`null` = none); the web pre-fills it from the phone, the server never infers it.
- **Revisions as the undo source.** Every family change by a member or an admin writes a `person_revisions` row (`before`/`after` snapshots, discriminated by `type`) in the same transaction as the change, plus the usual `audit_logs` row with ids and field names only. The revisions table **holds PII**: admin-only reads, never copied into `audit_logs` or logs, 1-year retention by a cleanup job. Every snapshot carries `personId` (DB CHECK, Security L2), so `POST /api/admin/people/:id/revisions/purge` (`{ confirm: true }`) can erase all history about a person for a removal request, also after the person is deleted. "Deshacer" (`POST /api/admin/revisions/:revisionId/revert`) restores `before` (or removes/re-adds the relationship) and records a `person.revert` revision linked by `reverted_by_revision_id`. Photo changes are recorded but not revertible (old objects are deleted). History list: `GET /api/admin/people/:id/revisions`.
- **Routes** (final): admin `POST /api/admin/people`, `PATCH|DELETE /api/admin/people/:id`, the revisions routes above, and `/api/admin/relationships`; member `POST /api/family/people`, `PATCH /api/family/people/:id`, `DELETE /api/family/people/:id`, and **no member relationship routes**.
- **WP-4.1 additions** (implementation decisions; details in `docs/coordination/WP-4.1.md`):
  - The circle also contains the people **a member created themself** and attached, by their own member edge, to someone already in their circle (bounded by the same depth), so a member can correct the sibling or grandchild they just added. It cannot reach anyone else's relatives: a member edge always joins a person that member created to someone already in their circle. The walk covers **unlinked** additions only and stops at linked ones (PR #46 L1): once an addition gets an account, the creator keeps it only through the normal rules (e.g. their own child over a qualifying edge).
  - **Self field set** (PR #46 L2): on their own linked person a member may change name, nickname, branch, birth year/date, birthplace and bio, through `PATCH /api/family/people/:id` or `PATCH /api/family/me` (same set). `deceased`, `deathYear` and `deathDate` of a **linked** person are admin-only: `PATCH /api/family/people/:id` answers 403 `FORBIDDEN` + `ADMIN_ONLY_FIELD` (`FamilyIssueCode`, open detail-code list), and the legacy `PATCH /api/family/me` strips them. Members may still record the death of an unlinked relative in their circle.
  - `GET /api/admin/family/activity` (admin-only, keyset-paginated, filter by actor and action) is the global feed of every revision ("admins see every change and can undo it", owner).
  - `DELETE /api/admin/people/:id?purgeHistory=true` purges the person's revisions first and records none for the delete. Every person delete revokes the person's pending invites in the same transaction. `PATCH /api/admin/people/:id` never moves a linked person to another account in one step (409 `PERSON_LINKED_TO_OTHER`; unlink first).
  - Admins calling the member write routes get full scope (admin edges).
- **Error detail codes** (open channel of §4; `ErrorCode` stays closed): `FAMILY_NOT_IN_CIRCLE`, `PERSON_LINKED_TO_OTHER`, `PERSON_HAS_RELATIONSHIPS`, `NOT_CREATOR`, `MERGE_BOTH_LINKED`, `MERGE_CONFLICT`, `MERGE_NOT_REVERTIBLE` (WP-4.5) (`FamilyIssueCode`, `family.ts`), `INVITE_PERSON_DECEASED`, `INVITE_PERSON_REQUIRES_BOUND`, `PERSON_HAS_PENDING_INVITE` (WP-4.2) (`InviteIssueCode`, `auth.ts`).
- **Invites linked to people (WP-4.2).** `personId` only on email-bound invites (400 `INVITE_PERSON_REQUIRES_BOUND`, checked before any lookup), for a living person (400 `INVITE_PERSON_DECEASED`) without an account (409 `PERSON_LINKED_TO_OTHER`) and without another pending invite (409 `PERSON_HAS_PENDING_INVITE`), all under a row lock on the person. On accept the person row is locked **before** the invite row (the same order as a person delete, whose FK action touches `invites`) and re-checked: the invite still email-bound (an open link naming a person never links it, Security L1 PR #44), the person still there, unlinked and living, else the account gets a new person and the `invite.accepted` audit row records `personLink: "fallback"`, `requestedPersonId` and `personFallbackReason` (ids and an enum only). `people.user_id` is unique, so a person never holds two accounts. Admins read `AdminInviteListItem.person` (`{ id, fullName }`, optional on the wire) and the picker `GET /api/admin/invites/people[/:id]` (`AdminInviteCandidate`: years, branch, nickname, `linked`, `pendingInvite`; never the account id).
- **Merge semantics ("Fusionar personas", WP-4.5; people only, no account merge).** Admin-only. `POST /api/admin/people/:id/merge` (`:id` = the person that **stays**, "keep"; body `personMergeInputSchema`: `duplicateId`, optional per-field `fields: { <field>: "keep" | "duplicate" }`) merges the duplicate into keep and deletes it, in **one transaction** with the lock order **tree → keep → duplicate → invites**. `GET /api/admin/people/:id/merge-preview?duplicateId=` runs the same code in a transaction that is always rolled back (`PersonMergePreview`: both sides, defaults, edges moved/dropped/in conflict, photo, account, invites, attendance, `blockers`).
  - **Account:** a linked duplicate moves its link to an unlinked keep (the duplicate is unlinked first; `person.user_unlinked`/`person.user_linked` audited). Both linked → 409 `MERGE_BOTH_LINKED`. Keep linked, duplicate not: the link stays.
  - **Fields:** `defaultMergeChoices` (contract): keep's value, filling keep's blanks from the duplicate; a full date only when it falls in the resulting year; `deceased` from the duplicate only when it says the person died. `fields` overrides per field (an explicit `"keep"` keeps a blank). The result goes through `personDatesIssue()` (400).
  - **Relationships:** the duplicate's edges are re-pointed to keep with the **same id, `created_by_user_id` and `created_by_member`** (so the qualifying-circle rule still decides whether a member edge counts), each through the cycle and 2-parent checks. Exact duplicates of keep's edges and keep↔duplicate links are dropped. Any failure → 409 `MERGE_CONFLICT`, one detail per edge (`path: "relationships.<id>"`, kind in the message).
  - **Photo:** keep's tree photo stays, else the duplicate's moves to keep. Every other object of the duplicate's tree photo (a losing photo, pending uploads) is deleted after the commit through WP-4.3's `personPhotoObjectKeys`/`deletePersonPhotoObjects`; pending `person_photo_uploads` rows cascade with the duplicate (their keys carry its id), they are not moved.
  - **Other references to `people.id`:** invites name keep afterwards (history); a pending one stays pending only if keep can still be invited (unlinked, living, no pending invite of its own), else it is revoked and audited (`reason: "person_merged"`). An accept racing the merge (it read the duplicate as the invite's person, then the merge committed) re-reads `invites.person_id` under the invite lock and, if the invite now names keep, retries **once** on keep with the usual person → invite lock order and the usual re-checks (WP-4.6); a second move falls back to a new person as before. `cuencada_attendance` rows move, or are dropped where keep already has that edition. The duplicate's own revisions keep its id in their snapshots (`person_id` becomes `null`).
  - **History:** one `person.merge` revision (action added by the expand-only migration 0006): `before` = a `merge` snapshot (`personId` = keep, `duplicatePersonId`, both person snapshots, the duplicate's creator, keep's edge ids, the duplicate's edges with their outcome and provenance, photo flags and `photo_updated_at`, moved/revoked invite ids, moved/dropped attendance), `after` = keep's result snapshot. No emails, contacts or object keys. The purge matches `duplicatePersonId` too. Audit `person.merged` with ids and counts only.
  - **Undo ("Deshacer" on the `person.merge` row):** within the 1-year retention window and only when nothing changed since: keep still has exactly the merged values, edges and photo, and there is **no later revision about either person**; otherwise 409 (stale), or 409 `MERGE_NOT_REVERTIBLE` if the duplicate's id is taken. It is a **full** undo, including a moved account link: the duplicate is re-created **with its old id**, its values, creator and link (moved back from keep), its photo if it had moved, its edges with their original ids and provenance (re-checked for cycles and parents), its attendance (dropped rows re-created) and its invites (revoked ones stay revoked). A losing photo deleted at merge time and dropped pending uploads are not restored. Unlike a 4.1 undo, restored edges keep their original provenance (they were never the admin's choice).
  - **Possible duplicates:** `GET /api/admin/family/duplicates` (offset cursor): same normalized name (case, accents, spaces and punctuation ignored) or one extra trailing word (a second surname; the shorter name has ≥ 2 words), with birth and death years within one year when both are known; plus invite fallbacks from the audit (`personLink: "fallback"` with `requestedPersonId`). The suggested keep is the requested tree person, else the one with more relationships, then the older. Both linked → listed with `mergeable: false`. No account ids.

### 7. Events ("Eventos", WP-5)

Contracts and the events migration come from WP-5.2 (`packages/types/src/events.ts`, details and the route list in `docs/coordination/WP-5.2.md`); WP-5.3 (server) and WP-5.4 (web) implement them. These rules are **binding** for both. Every event route is for **verified** members (`requireVerifiedEmail`, like the gallery); "member" below means a verified, active member, and "admin" the database role.

- **Model.** An event has `status` (`draft` | `published` | `hidden`), `visibility` (`members` | `participants`) and participants with a `role` (`organizer` | `participant`). Any verified member may create an event and becomes its organizer. `(year, slug)` is unique. **Collision handling is visibility-independent** (Security M1, PR #52, CWE-203): for members the slug is always `memberEventSlug(title)`: `slugifyEventTitle` (accent folding shared with the web) plus a random 4-character base32 suffix, **every time, collision or not** (e.g. `carne-asada-k7q2`), and the create/update schemas do not accept one. On the rare unique violation the server retries with a fresh suffix, never the bare slug. Neither the slug's shape nor the response therefore depends on events the caller cannot see. The slug does not change when the title does. Only admins type slugs (`POST /api/admin/events`, `PATCH /api/admin/events/:id`; a taken one is 409 `EVENT_SLUG_TAKEN`, which reveals nothing to someone who sees every event). Dates are both-or-neither; `year` is the year of `startsAt` **in the event's timezone** when dated (DB CHECK `events_year_check`), else chosen. Every write runs `eventDatesIssue()` on the merged row.
- **Who can see an event** (detail, list, participants, cover):
  - `published` + `members` → every member;
  - `published` + `participants` → its participants and admins;
  - `draft` → its organizers and admins;
  - `hidden` → admins only (only admins set or clear `hidden`).

  An event the caller cannot see is **404 `EVENT_NOT_FOUND`** on every route, including by id, so its existence does not leak (never 403). Lists apply the same predicate in SQL (one `eventVisibleSql(viewer)`), and hidden events appear only in `GET /api/admin/events`.
- **Chat and albums** (reading and posting messages, listing and uploading media, the album's media by id): participants and admins. A member who can see a `members` event but has not joined gets 403 `EVENT_NOT_PARTICIPANT` (the page offers "Me apunto"). An admin who is **not** a participant and opens a `participants` event's detail, chat or media is audited as `event.admin_viewed` (`metadata.surface`: `detail` | `chat` | `media`), at most **once per admin per event per hour** (the first surface in the window is recorded); admins on `members` events are not audited.
- **Managing** (edit fields, visibility, publish/unpublish, participants and roles, albums, cover): organizers and admins; others who can see the event get 403 `EVENT_MANAGE_NOT_ALLOWED`. Organizers move `draft` ↔ `published` (`first_published_at` is set once and never cleared); `hidden` is admin-only (403 `FORBIDDEN`).
- **Joining.** Self-join (`POST /api/events/:id/join`, "Me apunto") only for **published `members`** events; anything else visible answers 403 `EVENT_JOIN_NOT_ALLOWED` (admins included). `participants` events are organizer/admin-added only. Added users must be active, verified members (organizers pick from the directory; admins may add any member by id). Joining or being added makes the chat room visible at once.
- **Leaving.** Any participant may leave (`DELETE …/participants/me`), except the **last organizer** (409 `EVENT_LAST_ORGANIZER`; also for removing or demoting them). An event whose last organizer's account is deleted keeps running without one; admins can promote someone.
- **Deleting.** Admins always; an organizer only while the event is a **draft with no media** (any `media_items` row in its albums, soft-deleted included), else 403 `EVENT_DELETE_NOT_ALLOWED`. `media_items.album_id` is `ON DELETE RESTRICT`, so an admin delete first hard-deletes the album media rows in the same transaction and removes their objects (and the cover objects) after the commit. Participants, albums, cover uploads and the chat room (with its messages) cascade.
- **WebSocket.** Frames of an event room (`message`, `message_deleted`, `room_preview`, `typing`) reach **only** its participants and admins: the hub's fan-out takes a per-room recipient predicate backed by a per-room participant set, invalidated on every participant, status or visibility change. When a member loses access (removed, left, visibility tightened to `participants`, hidden, deleted), the server sends them `room_removed { roomId }`, drops their typing state and stops delivering the room. A `send` to a room the user cannot read is refused like today (`FORBIDDEN` error frame). Presence stays global (it lists user ids only).
- **Media scope.** Every media row has exactly one scope (DB CHECK): an edition or an event album. One `mediaScopeSql(viewer)` decides visibility for both, and **every** by-id route (`GET|PATCH|DELETE /api/media/:id`, `confirm`, `report`) checks it, answering 404 outside scope. Keys are server-generated under `media_items.storage_prefix` (`events/{eventId}/{albumId}`; legacy edition rows have `null` = `cuencadas/{year}`).
- **Privacy of participants.** `EventParticipant.userId` is present only for the caller's own row, for callers who can manage the event, and for participants listed in the directory and active; otherwise it is absent (§2 pattern). No email or contact is ever part of an event response. Audit metadata holds ids, field names, enums and counts, never titles or names.
- **Backward compatibility.** `ChatRoom.event` and `MediaItem.album`/`event` are optional on the wire; `MediaItem.cuencadaId`/`year` became nullable (`null` only for album media). Older clients drop the unknown `room_removed` frame and show an `event` room with the default icon.
- **Error detail codes** (open channel of §4; `EventIssueCode` in `events.ts`): `EVENT_NOT_FOUND` (404 `NOT_FOUND`), `EVENT_NOT_PARTICIPANT`, `EVENT_JOIN_NOT_ALLOWED`, `EVENT_DELETE_NOT_ALLOWED`, `EVENT_MANAGE_NOT_ALLOWED` (403 `FORBIDDEN`), `EVENT_SLUG_TAKEN` (admin routes only), `EVENT_ALBUM_NOT_EMPTY`, `EVENT_LAST_ORGANIZER` (409 `CONFLICT`), sent as `details: [{ path: "event", message, code }]` (`path: "slug"` for the slug).
- **Security requirements for WP-5.3** (Security review of PR #52; binding):
  1. **Visibility first, everywhere.** One SQL predicate (`eventVisibleSql(viewer)`) used by every list, by-slug and by-id route; an invisible event answers 404 `EVENT_NOT_FOUND` **before** any other check or code path runs (no 403, no validation detail, no timing branch on the event's state). The media by-id routes (`GET|PATCH|DELETE /api/media/:id`, `confirm`, `report`) apply the same rule through `mediaScopeSql(viewer)`.
  2. **Who can be added, and how much.** Server-side: a non-admin organizer may add only **listed, active, verified** members (the same set the directory shows); admins any active member. Participant cap `EVENT_PARTICIPANTS_MAX` = 200. Rate limits: participant writes ~100/h per user, event creation ~10/day per user plus a cap on open drafts per user. Every participant change is audited with ids only.
  3. **Consent.** Being added to a `participants` event creates an in-app notice (who added you, which event) with a one-tap "Salir". Later (backlog): a profile setting "only admins may add me to events".
  4. **Participant PII.** `EventParticipant.avatarUrl` follows the unlisted/disabled avatar rules (as chat senders and `resolvePersonPhoto`); `userId` per §7 above; never emails or contacts.
  5. **Admin-read audit.** `event.admin_viewed` is written **before** the data is returned, and the read fails (500) if the write fails. The once-per-admin-per-event-per-hour dedupe is race-free: an upsert/insert-on-conflict on a dedupe key (e.g. a small table or unique index on `(admin, event, hour bucket)`), not a read-then-write.
  6. **Chat.** The per-room recipient check is the **only** fan-out path (no broadcast bypass for any frame type). The participant set is refreshed on every participant, status or visibility change **before** clients are told about the change. A user who loses access gets `room_removed` and then no further frames for that room, `room_preview` and `typing` included. Every inbound frame and every history read re-checks access.
  7. **Media.** `storage_prefix` is always derived server-side from the album row (`events/{album.eventId}/{album.id}`), never from input; `confirm` rejects an item whose keys do not sit under its row's prefix; upload intents and confirms re-check participation (and visibility) at that moment.
  8. **Cover.** The full avatar pipeline (MIME allowlist, magic bytes, size, pixel cap, EXIF/GPS strip, WebP re-encode, crop clamp). Organizers and admins only, re-checked at confirm. Replaced and removed covers' objects are deleted. A cover URL is never presigned for a caller who cannot see the event.
  9. **PII scan additions:** an unlisted participant's id and avatar must not appear in event responses to other members; a `participants` event's title must never reach a non-participant (lists, chat room list, media `event` refs, admin-only fields).
- **Security requirements for WP-5.4:**
  - An invisible event and a missing one look identical: "No encontramos ese evento" (no hint that it exists).
  - The participant picker shows listed members only (the directory), with consent copy ("Le avisaremos y podrá salir cuando quiera").
  - Handle `room_removed`: drop the room from the list, close the open conversation if it is that room, and clear its cached history.
  - Reuse the gallery uploader and grid and the WP-4.3 `ImageCropper` (16:9 via the new `aspect` option); no new upload path.
  - Slugs are never typed by members. The form previews the URL as `slugifyEventTitle(title)` followed by a short code, with the copy "la dirección lleva un código corto" (the real code comes back in the response). Admin screens may edit the slug.

## Review response (PR #2, round 1)

Changes made in response to the Security and Tech Lead reviews. Most are already reflected in the sections above.
- **Invite inspect** returns `emailMasked` instead of the full email.
- **Admin invites** require `sendEmail: true`.
- **`emailVerified`** is only granted for email-delivered invites.
- **Open invites** are limited to 20 uses and 14 days (superseded by WP-2.3b: 10 uses, 72 hours).
- **Media allowlist:** HEIC removed and QuickTime added (orchestrator decision).
- **Links** are canonicalized (`URL.href`); userinfo and single-label hosts are rejected.
- **Bidi and invisible characters** are rejected in names and file names, and stripped from chat bodies.
- **`timezoneSchema`** is verified with `Intl.DateTimeFormat`.
- **The WS ticket** is session-bound, and the proxy-log redaction requirement is added.
- **Client request types:** `XxxRequest = z.input` is exported for every input.
- **Deliberately not changed:**
  - `AuditLogEntry.entityType` stays a free string, so legacy rows still serialize.
  - Display names reject ZWJ, so emoji sequences are not allowed in names; chat bodies keep ZWJ.
- **Decided (T1, 2026-10-06):** unverified members (copy-link and open invites) get **403 `EMAIL_UNVERIFIED`** (403 `FORBIDDEN` until WP-0.8a, which split the code so the client shows "verify your email" only for this case) on the directory, the family tree and every other PII read. Those routes declare `config.requireVerifiedEmail: true` (the WP-0.4 guard reads `users.email_verified_at` from the database). T5 (directory, profile reads of other members) and T6 (family tree) enforce it. A member verifies through `POST /api/auth/email/verify-request` → `/verificar#t=…` → `POST /api/auth/email/verify`; a magic-link login or a password reset sent to the current address also verifies it. Own-profile routes and `/me` stay open to unverified members so they can see the prompt.
- **Decided (owner, WP-2.3 L2, 2026-10-06):** the gallery and the member edition details are also verified-only.
  - Covered routes: every media route (`GET /api/cuencadas/:year/media`, `GET|PATCH|DELETE /api/media/:id`, `POST /api/media/:id/confirm`, `POST /api/media/:id/report`, `POST /api/cuencadas/:year/media/uploads`) and `GET /api/cuencadas/:year/members` (WhatsApp group and album links).
  - Why: photos and uploader names reveal family membership just as the attendees list does.
  - Still open to unverified members: announcements, the RSVP summary (counts only), their own RSVP, their own profile and avatar, and `/me`.
  - Thumbnail and display images are presigned bucket URLs that only these routes hand out, so the gate covers them too.
  - Residual risk: email verification proves control of a mailbox, not family membership. A stranger holding a leaked open invite can verify their own address. Mitigated by the stricter open invites below (WP-2.3b).
  - Enforced and tested by `apps/server/src/__tests__/security/verified-gating.test.ts` and the authorization matrix.
- **Decided (owner, WP-2.3 security audit → WP-2.3b, 2026-10-06): stricter open invites.** Verifying an email proves mailbox ownership, not family membership, so a leaked open (not email-bound) invite link lets a stranger join. Therefore:
  - Open invites default to **5 uses and 72 h** and allow at most **10 uses and 72 h** (`OPEN_INVITE_*` in `packages/types/src/auth.ts`). `expiresInDays` stays in whole days, so the open maximum is 3 days (= 72 h). Enforced by `adminInviteCreateInputSchema` (defaults depend on `email`) **and** by a separate server-side guard in `POST /api/admin/invites`. Email-bound invites keep 1 use, default 7 days, maximum 30.

  - Every acceptance of an open invite emails every active admin an `admin-invite-accepted` notice (display name, invite note and short id, uses so far / allowed, bitácora link). No email address, like the other admin alerts. Queued after commit; bounded by its own daily cap, separate from the admin-account alert cap. Details: `docs/coordination/WP-2.3b.md`.

## Consequences

- Adding a field to a response means changing the interface **and** its schema. `satisfies` makes the compiler enforce this in one direction: a schema can't omit a field the interface requires.
- Phase-1 tracks can add schemas to their own module file, but must not rename anything exported here without going through the orchestrator.
- Web code must build the `packages/types` `dist/` before Vite dev (`turbo` already does this for `build` and `typecheck`).
